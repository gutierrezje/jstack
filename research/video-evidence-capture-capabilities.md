# Video evidence capture capabilities

Checked 2026-09-24 against primary documentation and local command help. This is a capability survey; no screen was recorded and no GitHub upload was made.

## Findings

| Path | Supported capture | Prerequisites and limits | Fit for Jstack evidence |
| --- | --- | --- | --- |
| Playwright-controlled web session | Playwright records a video per page when its `BrowserContext` is created with `recordVideo`; videos are finalized when the context closes. Playwright Test can retain videos on failure. | This records the page viewport, not the whole desktop. For an existing browser, `connectOverCDP` is Chromium-only and documented as lower fidelity. Its default context exposes current pages, but the docs do not promise that an already-created context can have video recording enabled afterward. `Video.path()` also throws for remote connections. | Preferred for reproducible web journeys the workflow can run in a Playwright-managed context. Do not claim capture of the currently controlled tab until an integration is demonstrated. See [Playwright video](https://playwright.dev/docs/videos), [BrowserType.connectOverCDP](https://playwright.dev/docs/api/class-browsertype), and [Video.path](https://playwright.dev/docs/api/class-video). |
| Existing externally controlled browser | macOS can record a selected portion or the display containing the browser. Whether a particular externally controlled tab can be attached to Playwright depends on how that browser was launched and its endpoint; this was not tested. Screen capture includes whatever appears in the selected area and can expose unrelated content. | Use only when the task needs the actual existing session and the capture area can be kept task-specific. Otherwise, reproduce the journey in a dedicated Playwright context. ## GitHub delivery

The supported route is GitHub CLI `--attach`, which uploads a local image or video and inserts the resulting GitHub-hosted URL into an issue, pull request, or comment. The CLI docs explicitly say videos render as players and cannot have alt text; up to 50 files can be attached per invocation. The repo needs push access. GitHub supports `.mp4`, `.mov`, and `.webm`; video upload limits are 10 MB on free plans and 100 MB on paid plans, with additional eligibility requirements above 10 MB. GitHub recommends H.264 for broad playback compatibility. See [GitHub CLI attachment docs](https://docs.github.com/en/github-cli/github-cli/attaching-files), [gh pr comment](https://cli.github.com/manual/gh_pr_comment), and [GitHub attachment limits and formats](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files).

The local `gh` is v2.101.0. Both `gh pr comment --help` and `gh pr edit --help` confirm `--attach` accepts an image or video. Prefer `gh pr edit` for Jstack's existing PR-description evidence workflow; no comment needs to be sent. Help states that videos render as players without alt text, and partial attachment failures can still update the PR before returning nonzero. Read back the PR before retrying. This documents CLI capability, not an upload performed here. The REST issue-comment API accepts a text body; the supported binary-upload workflow is the documented CLI attachment feature, so avoid inventing a direct REST upload flow. Use only the user’s already-configured `gh` authentication and require repository write access. A durable receipt should retain the uploaded GitHub URL plus capture type, scenario, and result; leave the one-off recording out of Git unless the repo explicitly versions test fixtures. See [gh pr edit](https://cli.github.com/manual/gh_pr_edit).

## Recommendation and uncertainties

Make Playwright video the default for browser journeys already run under Playwright; offer native screen recording for desktop/native-app journeys and `simctl` for iOS Simulator journeys. Deliver finished MP4/WebM through `gh ... --attach` and preserve the returned asset URL in the existing evidence receipt. Before wiring into automation, validate video playback in the target GitHub repository and keep within its size/access limits.

Untested: CUA-to-Playwright attachment for the active externally controlled tab; actual ScreenCaptureKit automation and TCC permission behavior in Jstack; `simctl recordVideo` because the local simulator service was unavailable; and the `gh --attach` upload/render path. No recorder was installed and no credentials were read.
